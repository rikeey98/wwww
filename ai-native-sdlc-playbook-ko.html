Why the lifecycle changes

코드는 더 이상
가장 느린 단계가 아니다

에이전트형 코딩 도구가 구현 속도를 크게 끌어올리면서, 오히려 계획·검토·승인·배포처럼 사람이 중심이던 주변 단계가 새 병목이 되기 시작한다.

전통적인 SDLC는 코드 작성이 오래 걸리고 비용이 많이 들던 시대에 맞춰 설계되었다. 제품 요구사항 문서, 추정 회의, 보안 검토, 단계별 승인 절차는 긴 개발 기간 동안 정렬과 책임 소재를 지키기 위한 장치였다.

하지만 구현이 몇 주에서 몇 시간으로 압축되면 균형이 바뀐다. 사람이 직접 모든 변경 줄을 읽고, 정해진 회의 주기에 맞춰 예외를 승인하는 방식은 에이전트의 생산량을 따라가기 어렵다. 따라서 AI를 코드 작성자에만 붙이는 것이 아니라 SDLC 자체를 AI가 읽고 움직일 수 있는 구조로 바꿔야 한다.

From pipeline to loop

AI-native SDLC란?

핵심은 “통제를 없애는 것”이 아니라, 기존 통제 목적을 유지하면서도 AI 속도에 맞게 집행 방식을 바꾸는 것이다.

선형 핸드오프 대신 각 단계가 다음 단계가 바로 읽을 수 있는 아티팩트를 남긴다. 요구를 정리한 intent.md, 설계를 담은 spec.md, 구현 계획인 plan.md, 코드와 테스트, PR 검토 결과, 운영 사고 기록이 연결된다.

이 연결고리 자체가 추적 가능한 감사 기록이 된다. 사람이 판단해야 하는 지점은 그대로 남지만, 사람은 매 단계의 문서를 처음부터 다시 작성하는 대신 에이전트가 만든 결과와 위험 신호를 검토하는 역할에 더 집중하게 된다.

Stage전통적 SDLCAI-native SDLC
Plan워크숍과 티켓, 회의, 수동 문서화를 거쳐 요구사항을 정리한다.아이디어와 문제를 원천에서 바로 정리해 intent.md라는 인간·기계 공용 아티팩트로 남긴다.
Design분석가와 디자이너가 각자 문서를 만들며 단계 사이에서 해석 손실이 생긴다.조직의 보안·브랜드·UX 규칙을 Skill로 적용하면서 요구와 설계를 한 세션에서 압축한다.
Build구현 방법이 엔지니어 머릿속에 머무르고 문서는 뒤늦게 작성되기 쉽다.plan.md, CLAUDE.md, Skills를 통해 계획과 팀 지식을 버전 관리 가능한 형태로 만든다.
Test단계 경계에서 QA가 몰아서 검증한다.구현 중 검증과 CI 평가(evals)를 지속적으로 실행한다.
Deploy모든 변경을 사람이 일일이 살펴보고 승인 주기마다 정책을 확인한다.다층 에이전트 검토와 Hook을 사용해 정책을 실행 시점에 강제하고, 사람은 중요한 승인에 집중한다.
Maintain운영 담당자가 지표와 장애를 감시하고 이슈를 다시 개발팀에 전달한다.에이전트가 이상을 진단하고 결과를 다시 intent.md 또는 작은 PR로 되돌려 루프를 닫는다.
각 단계는 다음 단계가 읽을 수 있는 “커밋된 아티팩트”를 남긴다.

The plays

6개 단계는 순서가 아니라
연결된 플레이들이다

각 플레이는 “무엇이 달라지는가 → 어떻게 시작하는가 → 어떻게 실행하는가 → 무엇을 통제하고 측정하는가”의 구조로 생각할 수 있다.

모든 조직이 Stage 1부터 완벽히 적용할 필요는 없다. 이미 CI가 잘 갖춰져 있다면 Test나 Deploy부터 개선할 수도 있다. 중요한 것은 각 플레이가 의존하는 앞단 아티팩트를 명확히 하고, 단계가 끝날 때 결과를 다음 단계가 읽을 수 있게 남기는 것이다.

01

Plan

아이디어가 누군가의 문서화 순서를 기다리지 않도록, 처음 말한 사람의 의도를 바로 버전 관리 가능한 아티팩트로 남긴다.

Capture as intent.md

출발점은 사람의 아이디어일 수도 있고, 티켓이나 운영 알람일 수도 있다. 중요한 것은 출처와 상관없이 한 가지 형태의 intent.md로 수렴한다는 점이다.

이 문서는 완성된 PRD가 아니라 “왜 이 일을 하는지”를 잃지 않게 붙잡는 proto-spec에 가깝다. 문제, 원하는 결과, 영향을 받는 사용자·시스템, 제약, 아직 답하지 못한 질문을 담는다.

Traditional

아이디어 → 백로그 → 유저 스토리 → 포인트 추정 → refinement 회의를 거치며 소유권이 여러 번 넘어간다. 엔지니어가 받을 때는 최초 의도에서 멀어질 수 있다.

AI-native

아이디어를 낸 사람이 에이전트와 바로 브레인스토밍하고, 결과를 intent.md로 남긴다. 다음 단계가 즉시 읽을 수 있고 수정 이력도 남는다.

실행 순서

문제를 평소 언어로 설명한다.형식적인 요구사항 문법보다 현재 못 하는 일, 영향을 받는 사람, 원하는 개선 상태를 말한다.
에이전트가 분석가처럼 질문하게 한다.범위, 사용자, 제약, 성공 조건, 제외 범위를 구체화한다.
조직 템플릿으로 intent.md를 생성한다.반복되는 작성 규칙은 Skill로 만들어 누구나 같은 품질의 문서를 만들 수 있게 한다.
작성자가 오해를 바로잡는다.AI가 정리했어도 의도를 승인하는 책임은 사람에게 있다.
공유 저장소에 커밋한다.작성자, 시간, 수정 이력이 기록되고 제품 책임자가 다음 단계 진행 여부를 판단한다.
intent.md · 예시
# Intent: 고객 상태 조회 셀프서비스

작성자: 고객운영팀
상태: draft

## Problem
고객이 처리 상태를 알기 위해 상담센터에 반복 문의한다.

## Outcome
포털에서 현재 상태, 다음 단계, 예상 처리일을 확인할 수 있게 한다.

## Affected users / systems
고객, 상담 담당자, portal-web, claims-api

## Constraints
새로운 개인정보를 세션에 저장하지 않는다.
기존 로그인 체계를 그대로 사용한다.

## Open questions
외부 협력사 사용자도 같은 상태 화면이 필요한가?

Governance

증거는 커밋된 intent.md와 Git 이력이다. 제품 책임자의 승인/거절 자체가 다음 단계로 넘어가는 게이트가 된다.

핵심 설계 포인트

Git을 모르는 비개발자가 아이디어 제공자라면 UI나 커넥터가 대신 커밋하도록 만들어야 한다. 사용자는 Git 조작이 아니라 의도 검토에 집중한다.

Leading첫 대화 → intent.md 커밋 시간

며칠·몇 주 걸리던 요구 구체화가 몇 시간 수준으로 줄어드는지 본다.

LaggingDesign 단계로 살아남는 intent 비율

무분별한 자동 문서화가 아니라 실제 가치 있는 아이디어가 선별되는지 확인한다.

02

Design

요구사항과 설계를 따로 넘기지 않고, 조직 정책을 에이전트의 작업 규칙으로 적용하면서 하나의 spec.md로 압축한다.

Requirements + Design in one working session

승인된 intent.md를 입력으로 받아, 에이전트가 기존 코드베이스와 조직 규칙을 읽으며 요구사항과 설계를 함께 작성한다. 보안, 컴플라이언스, 브랜드, UX 같은 기준은 사람이 나중에 기억해서 체크하는 항목이 아니라 Skill로 주입되는 제약이 된다.

제품 책임자는 문서를 직접 처음부터 쓰기보다, “이 스펙이 최초 문제를 제대로 해결하는가?”를 검토한다. 서로 충돌하는 정책이나 모호한 지점은 에이전트가 flagged concern으로 표시해 사람이 판단할 위치를 좁혀준다.

Traditional

분석가가 요구사항을 정리하고, 디자이너나 아키텍트가 다시 해석한다. 단계가 분리되어 책임은 명확하지만, 시간과 의미 손실이 커진다.

AI-native

intent.md와 조직 Skills를 함께 읽혀 한 세션에서 spec.md를 만든다. 제품 책임자는 결과와 위험 표시를 검토한다.

실행 순서

intent.md와 조직 규칙을 세션에 제공한다.브랜드·보안·UX 규칙을 파일 또는 Skill로 함께 로드한다.
설계와 요구사항을 동시에 작성하게 한다.기존 코드베이스에 어떻게 통합할지, 어떤 제약이 충돌하는지 명시적으로 요구한다.
제품 책임자가 문제-해결 적합성을 검토한다.스펙이 intent의 문제를 해결하는지, 열린 질문이 해소되었는지 확인한다.
flagged concern부터 처리한다.정책 소유자나 기술 리드와 협의해 모호한 위험을 Build 전에 없앤다.
spec.md를 커밋한다.무엇을 원했는지(intent)와 무엇을 만들기로 했는지(spec)가 한 쌍의 기록이 된다.
설계 생성 프롬프트 · 예시
intent.md를 읽고 기존 코드베이스에 통합할 요구사항/설계 문서를 작성해줘.

반드시 다음 규칙을 적용해:
- API 보안 Skill
- 디자인 시스템 Skill
- 접근성/UX Skill

결과는 spec.md 형식으로 작성하고,
정책이 충돌하거나 확신할 수 없는 부분은 "Areas of concern"에 별도 표시해.
엔지니어가 바로 구현 계획을 세울 수 있을 정도로 구체적으로 써줘.

Governance

정책을 몇 주 뒤 리뷰에서 발견하지 않고 스펙 작성 순간에 적용한다. 어떤 Skill 버전과 어떤 프롬프트가 사용됐는지도 버전 관리하면 감사 가능성이 높아진다.

Human gate

최종적으로 Build로 넘어갈지 결정하는 것은 제품 책임자와 필요 시 기술 리드다. AI는 위험을 드러내지만 승인 책임을 대신하지 않는다.

Leadingintent.md → spec.md 리드타임

요구 정리와 설계가 별도 프로젝트처럼 늘어지는 시간을 비교한다.

LaggingBuild 이후 spec 수정 횟수

구현이 시작된 뒤 요구가 뒤집히는 비율이 줄어드는지 추적한다.

03

Build

승인된 계획 없이 바로 코드를 만들지 않는다. 구현 지식과 팀 규칙을 사람이 기억하는 관행이 아니라 에이전트가 매번 읽는 파일로 만든다.

Plan mode를 기본 출발점으로

엔지니어는 spec.md를 주고 바로 구현을 시작시키는 대신, 먼저 계획 모드에서 파일 변경 범위, 작업 순서, 테스트 전략, 위험을 정리하게 한다. 계획이 틀렸다면 코드를 되돌리는 것보다 문서 한 장을 고치는 편이 훨씬 싸다.

좋은 plan.md는 이전 대화를 본 적 없는 엔지니어도 실행할 수 있을 만큼 구체적이어야 한다. 구현이 계획에서 벗어나면 코드만 고치지 말고 plan.md도 함께 수정해 감사 기록이 현실과 일치하도록 한다.

Traditional

구현 방법은 엔지니어 머릿속이나 짧은 티켓 댓글에 남는다. 리뷰어는 완성된 diff를 처음 보고 설계 수준의 문제를 뒤늦게 발견한다.

AI-native

읽기 전용 계획 단계에서 plan.md를 만든 뒤 사람이 승인한다. PR 검토 시 실제 diff가 이 계획과 일치하는지 확인할 수 있다.

plan.md · 예시
# Plan: 고객 상태 조회 셀프서비스

## Files that change
- portal/src/claims/StatusPanel.tsx (new)
- claims-api/routes/status.py
- claims-api/tests/test_status.py

## Order
1. 기존 인증 뒤에 상태 조회 endpoint 추가
2. endpoint를 사용하는 StatusPanel 작성
3. 포털 navigation에 연결

## Risks
claims-core API의 호출 제한을 넘지 않도록 캐시 필요

## Proof
- 네 가지 claim state에 대한 API 테스트 통과
- 승인된 화면 스펙과 UI snapshot 일치

CLAUDE.md — 팀의 작업 기억

CLAUDE.md는 새 팀원이 첫날 알아야 할 정도의 핵심 지식을 에이전트에게 제공하는 파일이다. 빌드/테스트 명령, 중요한 코딩 규칙, 아키텍처 경계, 에이전트가 자주 틀리는 점을 짧고 명확하게 유지한다.

원칙은 단순하다. 같은 실수를 두 번 보면 팀의 기억으로 승격한다. 단, 모든 것을 집어넣으면 컨텍스트가 오염되므로 오래된 지식은 계속 정리해야 한다.

CLAUDE.md · 예시
# Payments service

## Commands
- Build: make build
- Test: make test
- Integration: make itest
- Lint: make lint

## Conventions
- Java 21 / Spring Boot 3
- 금액은 double 대신 BigDecimal
- 모든 endpoint는 integration test 필요

## Architecture
- api/: REST controller
- core/: domain logic
- adapters/: external system access

## Things the agent often gets wrong
- dependency version은 임의로 올리지 않는다
- legacy v1/는 변경 금지, 신규 변경은 v2/에 작성

Skills — 조직 지식을 실행 가능한 규칙으로

팀 내부 정책 중 “항상 같은 방식으로 적용되어야 하는 것”은 Skill로 만든다. 예를 들어 외부 API 보안 기준, 브랜드 문구 규칙, 데이터 분류 정책처럼 반복 적용이 필요한 지식을 SKILL.md로 패키징한다.

Skill은 에이전트가 적절한 상황에서 규칙을 읽게 만드는 강한 가이드지만, 반드시 지켜져야 하는 통제라면 뒤 단계의 deterministic Hook이나 PR 검증과 결합해야 한다.

.claude/skills/secure-api-review/SKILL.md · 예시
---
name: secure-api-review
description: 외부 공개 API를 만들거나 수정할 때 적용
---

# Secure API review

1. Authentication
   - 모든 endpoint는 gateway JWT 필요
2. Input validation
   - OpenAPI schema에 따라 request body 검증
3. Audit
   - 상태 변경 요청은 audit event 기록
4. PII
   - pii 필드는 log / error message에 노출 금지

완료 전에 scripts/check-endpoints.sh를 실행하고 결과를 요약에 포함한다.
기존 Jira/ServiceNow가 있다면?

모든 것을 Markdown으로 옮길 필요는 없다. 각 아티팩트마다 “어디가 source of truth인지” 하나만 정하고, 다른 시스템에는 링크나 commit SHA를 남기는 방식으로 공존할 수 있다.

Leading첫 구현 패스에서 바로 merge되는 비율

계획 품질이 높다면 구현 재시도가 줄어든다.

LaggingPR 재작업 횟수 + plan 일치도

최종 diff가 승인된 계획을 얼마나 잘 따르는지 확인한다.

04

Test

테스트를 마지막 QA 관문으로 두지 않고, 에이전트가 작업 완료를 주장하기 전에 증거를 제출하게 만들고 구성 변경 자체도 eval로 회귀 테스트한다.

“완료”에는 증거가 붙어야 한다

에이전트는 코드가 그럴듯하다는 이유만으로 완료를 선언하면 안 된다. 빌드, 단위 테스트, 통합 테스트, lint, 필요 시 화면 diff를 실행하고 실제 출력과 함께 결과를 보고해야 한다.

더 강한 통제가 필요하면 Hook으로 “검증 명령을 수행하지 않으면 완료 보고 불가”를 강제할 수 있다. 수정 작업에서 테스트 파일 자체를 바꾸지 못하게 막으면, 실패를 테스트 삭제로 숨기는 경로도 차단할 수 있다.

CLAUDE.md · verification block
## Verifying your work

- Build: make build
- Test: make test
- Lint: make lint

완료를 보고하기 전에 세 명령을 모두 실행한다.
테스트가 실패하면 테스트를 지우지 말고 구현을 고친다.
최종 요약에는 실행한 명령과 핵심 결과를 포함한다.

Continuous evals in CI

AI 에이전트의 프롬프트, 모델, CLAUDE.md, Skills, Hooks가 바뀌면 사실상 “개발 도구의 행동”이 바뀐다. 따라서 코드 회귀 테스트처럼 에이전트 구성에도 회귀 테스트가 필요하다.

실제 업무에서 대표 과제를 20~50개 모아 eval 세트를 만들고, 기대 결과를 테스트·lint·정책 준수 같은 체크로 정의한다. 이후 에이전트 구성 변경 PR이나 정기 스케줄에서 비대화식으로 실행한다.

실제 업무 사례를 eval 데이터로 수집한다.장난감 예제보다 최근 팀이 실제 해결한 과제를 쓰는 편이 좋다.
각 과제의 합격 조건을 명시한다.테스트 통과, lint clean, 특정 정책 유지, 동작 보존처럼 자동 확인 가능한 조건을 우선한다.
에이전트 구성 변경 시 자동 실행한다.CLAUDE.md, Skill, Hook 변경은 코드와 동일한 수준의 회귀 테스트 대상이 된다.
운영 사고를 새 eval로 영구화한다.한 번 생긴 장애가 같은 방식으로 다시 발생하지 않게 방어막을 쌓는다.

Evidence

실제 테스트 출력, 빌드 로그, 화면 비교 결과가 검증 증거가 된다. 세션 로그와 CI 체크 결과가 감사 기록으로 남는다.

Why it matters

리뷰어는 “테스트를 정말 돌렸나?” 같은 기계적 질문보다 의도, 위험, 사용자 영향에 시간을 쓸 수 있다.

LeadingAgent-written PR의 첫 CI 성공률

작업 완료 전 자체 검증이 제대로 작동하는지 본다.

LaggingPR review time / change failure rate

검증 자동화가 실제 리뷰 시간과 운영 실패를 줄였는지 확인한다.

05

Deploy

모든 줄을 사람이 직접 검토하는 방식 대신, 여러 층의 에이전트 검토와 deterministic gate를 조합해 사람의 판단을 위험한 지점에 집중시킨다.

Agentic review + human escalation

PR이 생성되면 에이전트가 먼저 intent.md, spec.md, plan.md, 실제 diff를 함께 비교해 “원래 목적과 구현이 일치하는지”, “중요 정책을 어겼는지”, “테스트 증거가 충분한지”를 확인한다.

모든 PR을 동일한 강도로 사람이 읽지 않고, 규제 코드·보안 민감 경로·큰 blast radius처럼 조직이 중요하게 분류한 경우에만 사람이 필수 승인자로 들어오게 할 수 있다. 즉 사람을 제거하는 게 아니라 사람이 봐야 할 변경을 더 정확히 골라내는 구조다.

Hooks — 승인 정책을 실행 순간에 강제

Skill이 “이렇게 해야 한다”를 가르치는 규칙이라면 Hook은 “이 조건이면 실행을 막는다”에 가깝다. 운영 배포, 보호 경로 수정, 외부 네트워크 접근 같은 행동 직전에 스크립트를 실행해 허용·추가 승인 요청·차단을 결정한다.

.claude/settings.json · hook 예시
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh"
          }
        ]
      }
    ]
  }
}
production-gate.sh · 재구성 예시
#!/usr/bin/env bash
cmd=$(jq -r '.tool_input.command' < /dev/stdin)

if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
  if [[ -z "${RELEASE_APPROVAL:-}" ]]; then
    echo "운영 배포에는 release approval이 필요합니다." >&2
    exit 2
  fi
fi

exit 0

Enterprise에서는 managed settings로 못 끄게

규제가 강한 조직에서는 로컬 설정만으로 충분하지 않다. 민감 파일 읽기 차단, 임의 네트워크 접근 차단, 허용된 명령만 자동 승인, sandbox 필수, 개인이 Hook을 끄지 못하게 하는 managed policy가 필요하다.

이런 구성은 “사람이 규칙을 기억해 조심한다”가 아니라 실행 환경 자체가 위반 경로를 없애는 방식으로 거버넌스를 바꾼다.

핵심 원칙

정책은 문서에만 있으면 속도와 함께 희석된다. 가능한 것은 Skill로 작업 중 적용하고, 절대 깨지면 안 되는 것은 Hook·CI·sandbox 같은 deterministic control로 막는다.

Leading자동 검토로 분류 가능한 PR 비율

사람이 모든 변경을 동일하게 보는 비용이 얼마나 줄었는지 본다.

Lagging배포 실패율 + 정책 위반 재발률

자동화된 gate가 실제 운영 안정성과 규제 준수에 기여했는지 확인한다.

06

Maintain

운영은 끝 단계가 아니다. 서비스에서 나온 신호를 에이전트가 진단하고, 작은 수정은 PR로, 큰 문제는 새로운 intent.md로 되돌려 전체 사이클을 다시 시작한다.

운영 신호가 다시 개발 입력이 된다

메트릭이 정상 범위를 벗어나거나 보안 스캔이 취약점을 찾으면 에이전트가 먼저 맥락을 모은다. 로그와 최근 배포, 관련 코드, 과거 유사 사고를 연결해 가설을 세우고, 수정 범위를 판단한다.

작고 명확한 문제라면 바로 제한된 수정 PR을 만들 수 있다. 반대로 여러 시스템에 영향을 주는 문제나 제품 결정이 필요한 문제라면 자동으로 intent.md를 만들고 Stage 1로 되돌린다.

Traditional

운영 담당자가 알람을 보고 티켓을 만들고, 담당 엔지니어가 맥락을 다시 수집하고, 나중에 수정이 시작된다.

AI-native

운영 신호와 조직 지식에 접근 가능한 에이전트가 즉시 진단을 시작하고, 변경 범위에 따라 PR 또는 새 intent로 라우팅한다.

On-call에서도 같은 루프 유지

장애가 Slack/Teams 같은 협업 채널에서 시작되더라도 원리는 같다. 대화 맥락, 진단 과정, 사람의 승인, 수정 결과가 한 채널에 남고, 에이전트가 관련 도구에 연결되어 있다면 메트릭 정상화까지 확인할 수 있다.

사후에는 post-mortem과 재발 방지 지식을 버전 관리 파일에 남기고, 필요하면 새로운 eval을 추가한다. 즉 운영 경험이 다음 에이전트 세션의 지식과 테스트로 다시 흡수된다.

Maintenance에서 루프가 닫히는 두 가지 경로
Alert / ticket운영 신호
Diagnosis로그·코드·최근 변경 분석
Small?작으면 PR
Large?크면 intent.md
PR은 Deploy gate로, intent.md는 Plan으로 돌아간다.

운영 자동화의 경계

에이전트가 자동으로 조사할 수 있어도, 고위험 운영 변경과 규제 대상 액션은 기존 승인 체계를 Hook으로 유지해야 한다.

학습 루프

사고 원인, 해결책, 새로운 eval, CLAUDE.md/Skill 수정이 다시 Build/Test 단계의 품질을 높인다.

Leading알람 → 첫 진단 / 첫 패치 시간

사람이 호출되고 맥락을 모으는 시간을 얼마나 줄이는지 본다.

Lagging같은 유형 사고 재발률

운영 경험이 실제 eval과 지식 파일에 흡수되어 재발을 막는지 확인한다.

Closing thoughts

전체 생명주기를
에이전트가 읽을 수 있게

AI-native SDLC의 본질은 코딩 도구를 더 많이 쓰는 것이 아니라, 사람의 판단은 중요한 게이트에 남기고 나머지 흐름을 아티팩트·자동 검증·정책 집행으로 연결하는 데 있다.

이 구조에서 Git이나 다른 source of truth는 단순 코드 저장소가 아니라 요구, 설계, 계획, 구현, 검증, 승인, 운영 학습이 이어지는 감사 기록이 된다. 에이전트는 이 기록을 읽어 다음 행동을 시작하고, 사람은 결과의 의도와 위험을 판단한다.

루프는 계속 돈다.
사람의 판단은 그 위에 남는다.
이 페이지를 실무 체크리스트로 쓴다면

먼저 한 프로젝트에서 intent.md → spec.md → plan.md 세 파일만 연결하고, 다음으로 CLAUDE.md와 반복 정책 Skill을 정리한 뒤, Test/Deploy 단계에 eval·Hook을 붙이는 순서가 부담이 적다. 마지막에 운영 사고를 다시 intent/eval로 되돌리면 루프가 완성된다.

비공식 한국어 재구성 · 원문의 아이디어와 공개된 구조를 바탕으로 학습용으로 재서술했습니다.
